## 1. Windows

### 1.1 Windows 桌面插件

状态:[未定]

- **定位**:与 macOS、Linux 一样,作为 note.md 插件提供入口和专用文档视图,编辑区用本机原生富文本控件(旧主规范 §1、§4)。
- **现状**:**未交付**。插件二进制只有 `aarch64-apple-darwin` 和 `x86_64-unknown-linux-gnu` 两个目标;宿主在其他系统上挂载原生编辑面会报“当前系统尚不支持 Sumi 原生编辑(支持 macOS 13+ 与 Linux)”。见源仓库 `plugins-src/write/manifest.v2.json`、`src-tauri/src/sumi/mod.rs`。
- **旧规范的选型方向**:优先验证在 Tauri 里内嵌原生 Win32 Rich Edit HWND。WinUI `RichEditBox` 需要额外的宿主集成,不能假定可以直接嵌入。候选窗口位置(`ImmSetCandidateWindow`)要逐个输入法验证。
- **旧规范的验收口径**:Windows 输入法正常工作(原 P3 阶段的一项)。
- **没有定的**:是否做、何时做、用哪个控件、Fcitx5 for Sumi 一类的增强候选在 Windows 上是否有对应物。

## 2. Android

### 2.1 Android 应用

状态:[未定]

- **定位**:独立的原生应用,不依赖桌面 note.md,也不依赖完整 vault(旧主规范 §1)。
- **旧规范的选型方向**:简单写作优先用 `EditText` 加 spans 的薄层。Aztec 是 `EditText` 的扩展,偏 HTML,许可是 MPL-2.0。Compose Rich Editor 是另一套不依赖 WebView 的文本框架,需要单独评估。基于 WebView 的编辑器不算系统原生方案。
- **输入法**:用系统输入法。主题属于输入法服务(`InputMethodService`)自己,编辑器不承诺能跟主题同步配色。
- **旧规范的验收口径**:原 P2 阶段把 Android 和 iOS 放在一起,退出条件是“与 Mac 混合并发 / 离线夹具通过,移动端电量与后台重连通过”。
- **复用方式**:如果将来要做,应与 iOS 同一思路,共用 Rust `core` 与 `session/`,不另写一套 CRDT 或行时间实现。这是按设计文档“两端实现不分叉”的反目标推出来的,尚未单独确认。
- **没有定的**:是否做、何时做、FFI 方式。

## 3. ESP32

### 3.1 ESP32 设备客户端

状态:[未定]

- **定位**:独立的设备客户端。**板型、内存、屏幕和输入硬件都没有选定**,能力边界需要单独验证(旧主规范 §1、§6.4)。
- **工程参考**:按用户指定,以 Draftor 为主要工程参考。核对的是固定源码 `d36fb31693991d22197fe9101d7b1114ade3cc10`(Alpha 2.1),此后 main 分支的变化不算已验证。Draftor 是自研的 C++ 编辑与绘制链路(Document / BodyEditor / LayoutEngine),不是一个可以直接装上的通用富文本控件。
- **中文输入**:bgIME 作为首选输入引擎来评估,它支持全拼、小鹤双拼和五笔 86。候选区和组合区由本机控制,可以固定在底部;只有提交后的文字才写入同步模型。
- **原型硬件参考**:ESP32-S3 N16R8(16 MB Flash、8 MB PSRAM)+ BLE 键盘 + TF 卡 + 300×400 ST7306 黑白红反射式 TFT。**这只是参考,不是用户已选定的硬件。** 这块屏不是电子墨水屏。灰阶、任意主题、字体缩放和底部候选区,都要按实际屏幕的能力验收。
- **容量**:Draftor 正常配置下正文为 64 KiB。这是**字节**预算,不能当作 6.4 万个汉字。加入 Markdown 元数据、outbox、TLS 和同步基线之后,要重新评估。
- **内核**:不能预先假定 ESP32 能跑完整的 Yrs。上游只有纯文本模型,没有本项目需要的 Markdown 样式模型,也没有行时间,这两样都要新增。坐标要映射,规则是绑定修订号的 UTF-8 字节 ↔ 共享协议 UTF-16 ↔ 字素,不能直接发送字节偏移。
- **离线合并**:要声称支持离线自动合并,必须先证明三件事:重连后能取回所需的基线;能为离线操作保留稳定的 actor 与位置映射,并与当前 CRDT 合并;日志整理之后仍有正确的恢复路径。证明不了,就只能标“在线接续 / 受限离线”,不能宣称全平台离线合并已完成。
- **存储**:板载闪存与 SD 卡上的文件布局要等硬件验证。始终不能把 RAM 里的正文当作已保存。
- **许可**:bgIME、词库和字体的资源量与许可证要分别核对,不能把整套资源一律按 Apache-2.0 重新分发。
- **旧规范的验收口径**(原 P4):逐项实测 UTF-8/UTF-16 映射、远端更新与撤销、BLE 加 Wi-Fi 负载、Markdown 样式、内存、字库、掉电和离线合并。

## 4. 桌面独立应用

### 4.1 何时从插件改为独立应用

状态:[未定]

桌面版现在是 note.md 的插件。独立应用不在近期范围内,只写进路线图,iOS 上线后再评估(设计 §2 **[用户定]**;第 5 期)。保持插件形态的理由见 [ADR 0008](../../adr/0008-standalone-repo-desktop-stays-plugin.md)。

满足下面**任意两条**,就启动桌面独立(设计 §9):

1. 过去一个季度里,因为原生编辑桥改动而被迫配套发宿主的次数,明显多于宿主自身需要的发版。
2. iOS 版证明了内核加原生界面的组合可以脱离宿主运行,而且维护成本可以接受。
3. 出现了不用 note.md、但想用玄霜写作的桌面用户需求。

独立时:

- 原生编辑桥(现在是 note.md 的 `tauri-plugin-native-editor/`)随之迁入 sumiwrite;
- note.md 改为只识别和阅读 `.writing.md`,不再提供写作编辑面。

第 1 条的“明显多于”没有量化的门槛,评估时由用户判断。[未定]

### 4.2 可独立更新的编辑模块

状态:[未定]

旧主规范把“让原生编辑能力不随宿主发版就能更新”列为远期目标,没有实现。现行的三层更新边界见 [notemd-desktop.md §4](notemd-desktop.md)。这一目标是否还需要,取决于 4.1 的评估结论。

## 6. 其他明确推迟的事项

### 6.1 定制输入法

状态:[未定]

旧主规范的 P5 阶段计划过按平台单独实现的定制输入法:候选固定在底部,配色与主题联动;编辑器只传经过授权的主题和几何参数,不传全文。各平台入口分别是 iOS 的键盘外观提示、Android 的系统输入法服务、macOS/Windows/Linux 的输入框架,不承诺跨系统共用同一个开关。退出条件是:输入法的生命周期、安全和无障碍都通过,编辑器不需要读取组字中的全文。

现状是:桌面上已经有独立项目 **Fcitx5 for Sumi**,提供增强候选,对接契约见 [notemd-desktop.md §6.3](notemd-desktop.md)。iOS 明确不做自定义输入法或键盘扩展(见 [ios.md](ios.md) 的“不做”)。其余平台怎么做,没有定。

### 6.2 iOS 的二维码配对与打字音效

状态:[未定]

- **二维码配对**:iOS 第一阶段只支持粘贴邀请文本。要支持二维码,得先改桌面插件,让它也能输出二维码,所以推迟(设计 §10.1)。
- **打字音效**:iOS 第一阶段不做,留到后续(设计 §10.1)。

### 6.3 逐笔回放

状态:[未定]

行时间只记每个逻辑行的首次书写与最后修改时间,首版**不做逐笔回放**。这是用户在旧主规范 §1 中确认的范围。是否以后再做,没有定。

### 6.4 尚待物理验证的平台能力

状态:[未定]

以下各项旧规范列为验收项,但至今没有物理证据。详见 [notemd-desktop.md §6.4](notemd-desktop.md) 与 [04-known-gaps.md](../../handoff/04-known-gaps.md):

- ARM64 Linux 版本;
- Hyprland 分数缩放;
- XWayland 下的表现;
- VoiceOver 等无障碍能力;
- 各平台的物理输入法终验。
