# 平台附录 · iOS/iPadOS 版

玄霜写作(Sumi Write)的 iOS/iPadOS 版是一个独立的原生应用,不依赖 note.md,也没有 vault。**本附录全部是计划**:还没有任何 iOS 发布,iOS 代码在 `apps/ios/`,M0、M1 正在实现,尚未交付。下文每一条都标 `[计划:iOS]` 或 `[未定]`,不能当作已存在的行为引用。2026-11 做过两次一次性试做(界面试做、M0 内核试做),代码不进仓库,结论记在 [§8](#8-试做记录),并写回了下文对应小节;试做结论是证据,不是交付。

- **来源**:设计文档 [`docs/superpowers/specs/2026-11-18-sumiwrite-extraction-design.md`](https://github.com/wizlijun/note.md/blob/0c11629f976226c688d186b13d4812da31073dc2/docs/superpowers/specs/2026-11-18-sumiwrite-extraction-design.md) §2、§4.3、§4.4、§5.4、§8、§10、§12(note.md 提交 `0c11629f`)。旧主规范 `2026-11-07-immersive-write-design.md` 中涉及移动端的条目也已对照。
- **归属标记**:**[用户定]** 是用户亲自拍板的;**[我的判断]** 是设计者的判断,用户可以推翻。两者均沿用设计文档原文。
- **共用规则**:iOS 与桌面共用纸页、Markdown 与行时间、同步、编辑体验、字体的规则,分别见 [01](../01-pages-and-storage.md)、[02](../02-markdown-and-line-time.md)、[03](../03-sync.md)、[04](../04-editing-experience.md)、[05](../05-fonts.md)。本附录只写 iOS 独有的部分。
- **技术选型**:[ADR 0010](../../adr/0010-ios-uikit-textkit2-uniffi.md)(UIKit + TextKit 2 + UniFFI)、[ADR 0011](../../adr/0011-ios-personal-use-identity-layer.md)(先自用,身份层分开)、[ADR 0012](../../adr/0012-shared-session-module.md)(共用会话模块 `session/`)、[ADR 0009](../../adr/0009-page-store-vs-vault-projection.md)(纸页存储与归档投影分开)。

**定位**:

- 第一阶段**先自用** **[用户定]**:走 TestFlight 或自签名安装,沿用现有的配对码,账号体系不动。
- 第一阶段**不公开发行** **[用户定]**:没有注册登录、多租户、付费,也不上 App Store。
- 技术栈是 **Swift 原生界面 + Rust 内核** **[用户定]**(设计 §4.4)。Tauri Mobile 这类跨平台壳已排除,因为它不是原生界面,输入法和键盘避让都做不好。
- 具体分层是界面用 UIKit/TextKit 2 加 SwiftUI,经 UniFFI 调用 Rust 内核 **[我的判断]**。这一层出自设计 §10.2 的架构图,设计没有给它标注归属,不属于 §4.4 的用户决定。
- 最低系统 **iOS 17 / iPadOS 17** **[我的判断]**。理由:TextKit 2 在这个版本上已足够稳定,自用场景也不需要照顾旧设备。

## 1. 范围

### 做

状态:[计划:iOS]

第一阶段做以下这些:

- **一页纸写作**:打开应用即恢复上次的纸页、光标和阅读位置。
- **纸页管理**:纸页概览、新建、上一页、下一页、移到废纸篓、从废纸篓恢复。
- **外观**:六种主题、字号、行距;第一阶段内置 Sumi Plex(IBM Plex Mono Light + IBM Plex Sans SC Light)、Sumi WenKai(LXGW WenKai Mono Lite)与 Sumi Zhaohua(朝华打字机,`ZhaohuaTypeWriter.ttf`,作者许可 `LicenseRef-TerryWang-Typewriter`,不是 OFL)三组字体,其余三组(油茶、朱雀仿宋、Unifont)仍按 [05-fonts](../05-fonts.md) 按需下载。iOS 安装包因内置朝华打字机增加约 27.5 MB。这是 iOS 平台的例外,不改 05-fonts 里宿主与插件包不内置字体文件的桌面规则 **[用户定]** 2026-11-20「全部照搬」;2026-11-21 增加朝华打字机:「请增加内置：朝华打字机」。
- **光标**:自绘竖线光标,可选呼吸或常亮。
- **输入**:系统输入法正常组字、选词。正文避让软键盘;接上硬件键盘后收回留白。接实体键盘时,应用内嵌的 Rime 输入法(共享包 RimeKit,词库为内置雾凇)接管按键,不经系统输入法就能打中文,规则见 [§3.6](#36-实体键盘的内嵌输入法) **[用户定]** 2026-11-20「让 ios ipados 的外置键盘输入可以有我们需要的输入法效果」。设置里可选切换中 / 英的快捷键(默认 Control + 空格,见 §3.6)。
- **快捷键**:iPad 硬件键盘支持快捷键,按规范中的语义映射。
- **同步**:离线可写,联网后自动合并;可以和桌面同时编辑同一页。
- **配对**:粘贴桌面端生成的邀请文本、填写同步服务地址,即加入同步空间。凭据存在钥匙串里。
- **导出**:当前纸页导出为 Markdown,走系统分享。
- **应用显示名** **[用户定]**:2026-11-20 用户决定 iOS 主屏与系统设置里的应用名一律显示 Sumi Write,不随系统语言切换;应用内文案仍称玄霜写作。这是 [00-product](../00-product.md) 命名表的 iOS 例外。
- **应用图标** **[用户定]**:2026-11-20 用户提供打字机图标(米色底、墨绿打字机、纸上打着 sumi),原图 1254×1254 缩到 1024×1024 放进 `apps/ios/SumiWrite/Assets.xcassets/AppIcon.appiconset/icon-1024.png`,圆角由系统加。
- **打字音** **[用户定]**:2026-11-20 用户决定纳入第一阶段,规则见 [§3.4](#34-打字音)。这推翻了设计 §10.1 把它列进“不做”的判断(那一条原是 [我的判断])。

### 不做

状态:[计划:iOS]

以下各项第一阶段明确不做。除注明外,均为 **[我的判断]**(设计 §10.1):

- vault、文件夹、文件名。
- 键盘扩展(自己的软键盘)。原先这一条是「自定义输入法或键盘扩展」;2026-11-20 用户决定在应用内嵌 Rime 输入法(见 [§3.6](#36-实体键盘的内嵌输入法)),删掉「自定义输入法」,只留键盘扩展。内嵌引擎只接实体键盘,不是键盘扩展,系统输入法照样可用。
- 专注窗口的固定尺寸规格。这在手机上没有意义;iPad 直接用系统的多窗口与全屏。
- 注册登录、付费、上架 **[用户定]**。设计 §2 把“iOS 第一阶段不做公开发行:没有注册登录、多租户、付费、App Store 上架”定为用户决定;设计 §10.1 的不做清单虽把它列在 [我的判断] 之下,以 §2 为准。
- 扫码配对。桌面端现在只输出邀请文本,没有二维码;要加二维码就得改桌面插件,所以留到后续。

## 2. 架构

### 2.1 四层结构

状态:[计划:iOS]

```
SwiftUI 外壳(纸页概览、设置、配对)
        │
UIKit 编辑面(UITextView + TextKit 2,自绘光标)
        │  编辑事务(修订号 + 可见 UTF-16 范围)
Swift 薄适配层(把 UIKit 回调转成会话调用,钥匙串读写)
        │  UniFFI
Rust:session(单一编辑 owner、组字期间暂缓远端更新、本机输入日志、
            崩溃恢复、同步协调与同步客户端)
      core(文档、SourceMap、存储、候选会话)
```

| 层 | 职责 | 不做什么 |
|---|---|---|
| SwiftUI 外壳 | 纸页概览、设置、配对界面 | 不碰正文,不碰 CRDT |
| UIKit 编辑面 | `UITextView` + TextKit 2 排版。自绘光标,压住系统光标。处理系统输入法组字、选区和键盘避让;把用户输入整理成编辑事务 | 不解析 Markdown,不写文件,不连网络 |
| Swift 薄适配层 | 把 UIKit 回调转成 `session` 调用,读写钥匙串 | 不含会话或同步逻辑 |
| Rust `session` | 单一编辑 owner;组字期间暂缓远端更新;本机输入日志;崩溃恢复;同步协调与同步客户端 | 不依赖 Tauri 和插件 SDK(第 3 期的完成标志) |
| Rust `core` | 文档、SourceMap、存储、候选会话;生成最小的规范 Markdown 事务 | — |

- **内核构建**:内核编成 XCFramework,由 UniFFI 生成 Swift 接口。
- **会话与同步逻辑不在 Swift 里重写** **[我的判断]**。这些逻辑目前分在两处:宿主的 `src-tauri/src/sumi/`(owner、组字防护、输入日志、恢复,约 8.7k 行),以及插件后台的 `sync.rs`、`coordinator.rs`、`durability.rs`(约 6k 行)。它们决定了数据不丢、合并正确,测试也最重。在 Swift 里再写一遍,就违反了“iOS 与桌面的 CRDT 或行时间实现不得分叉”这一反目标。所以第 3 期先把其中与宿主无关的部分下沉为 `session/`,iOS 直接用它(见 [ADR 0012](../../adr/0012-shared-session-module.md))。
- **线程**:持久化在后台线程做,输入线程不等锁。
- **证书校验**:插件后台的 WebSocket 用的是 `tokio-tungstenite` 的 `rustls-tls-native-roots` 特性(`plugins-src/write/backend/Cargo.toml`)。这套根证书加载方式在 iOS 上很可能不能用(**未实测**),所以下沉到 `session/` 时要换一种证书校验方式。这条已作为后果记进 [ADR 0010](../../adr/0010-ios-uikit-textkit2-uniffi.md)。

### 2.2 编辑事务的形状

状态:[计划:iOS]

- 编辑事务的形状与桌面原生编辑桥一致。原生回调带上修订号和可见文本的 UTF-16 范围,由内核生成最小的规范 Markdown 事务。桌面一侧的现行定义见[契约 §1.2 表 B](../../handoff/03-notemd-contract.md):`Edit` 是相对 `base_revision` 的 UTF-16 替换。
- 组字中的文字**不进 CRDT**。组字期间到达的远端更新先暂存,组字结束后再应用。这是内核 README 的既有规定,iOS 照做。
- 判定时机:在 `textViewDidChange` 里看 `markedTextRange`,为空才把编辑面的变化交给内核。系统软键盘的输入不经过 `pressesBegan`,按键种类(普通键、空格、回车、退格、拼音上屏)也只能在文字变更时识别;拼音被替换成更短的原拼音前缀算退格,被替换成汉字算上屏。两次试做都按这条做(见 [§8](#8-试做记录))。
- 编辑面与内核的差异按字素求公共前后缀,换算成 UTF-16 范围后调用内核的替换。内核拒绝(修订过期、切开字素)时以内核正文为准重置编辑面,不让两边分叉。这是 M0 试做的做法;M1 改为由编辑面直接给出范围时,拒绝后的处理照旧。
- 撤销与重做交给 CRDT 的撤销 owner,不用 UIKit 自带的撤销栈(桌面同样关闭了 AppKit 撤销)。M1 的做法:关掉 `UITextView` 自带的撤销栈,改为一个转发给内核 `undo` / `redo` 的 `UndoManager` 子类;粒度一次事务一步,内核撤销不合并相邻事务。详见 [§7.8](#78-撤销归属)。
- 一次事务被接受之前,必须先写进本机输入日志,和桌面“先记日志、再接受修订”的顺序一样。日志写失败时编辑面如何呈现(桌面的做法是 `draft_error`,保留可见文字但禁止继续修改),由 M2 定。[未定]

### 2.3 存储位置与钥匙串

状态:[计划:iOS]

- **纸页存储**:内核的 SQLite 保存完整的 CRDT 历史,是本机事实源,放在应用沙盒里(设计 §5.4)。iOS **没有归档投影**,不生成 `inbox/writings/` 目录,也不生成 `.writing.md` 文件(见 [ADR 0009](../../adr/0009-page-store-vs-vault-projection.md))。
- **钥匙串**:空间、设备凭据存在 iOS 钥匙串里,由 Swift 薄适配层读写。凭据不进纸页数据库、偏好或日志。
- **发行事务**:Bundle ID、签名身份、TestFlight 配置都不进仓库,仓库里只放凭据引用(设计 §12)。

以下待定:

- 钥匙串的服务名与访问组 [未定]。桌面 macOS 的服务名是 `com.notemd.sumi.credentials.v1`,iOS 是否沿用,由 M3 定。
- 沙盒内的具体目录 [未定]。旧主规范写的是“应用私有 Documents 内的 Markdown 快照与持久状态”;设计 §5.4 只写了“SQLite 放在应用沙盒里”。是否另存一份 Markdown 快照、放在 Documents 还是 Application Support,由 M2 定。

## 3. 交互

### 3.1 配对流程

状态:[计划:iOS]

1. 在桌面玄霜写作里生成一次性配对码(邀请文本)。邀请含 256 位密钥,5 分钟后过期(源仓库 `write-sync-worker/src/protocol.ts`:`invitationSeconds: 300`,密钥为 32 字节随机数)。
2. 邀请文本不适合手输,靠通用剪贴板或隔空投送传到手机上。
3. 在 iOS 的配对界面**粘贴邀请文本**,并**填写同步服务地址**。
4. 加入同步空间,凭据存入钥匙串。

- 配对界面**不出现管理员密钥**(见 5.1)。
- 邀请里的空间 ID 必须与目标服务返回的身份一致,服务地址的来源也必须一致,否则拒绝。这是桌面插件后台的现行校验(`plugins-src/write/backend/src/network.rs`),iOS 照做。
- 服务地址能否从邀请文本中自动带出:[未定]。现行邀请只含空间 ID、配对码和过期时间,不含服务地址。

### 3.2 键盘避让与硬件键盘

状态:[计划:iOS]

- 正文跟随系统软键盘的实际 inset 避让,用 `keyboardLayoutGuide` 跟踪。接上硬件键盘、软键盘收起后,收回底部留白。光标始终留在可用编辑区内,不被留白挡住。界面试做把编辑区底边约束到 `keyboardLayoutGuide.topAnchor`,并打开 `followsUndockedKeyboard`,在 iPhone 上可用;iPad 浮动与分离键盘未测。
- 键盘外观只能通过 `keyboardAppearance` 给系统有限的提示,不能保证与主题同色。
- iPad 硬件键盘的快捷键按 [04-editing-experience](../04-editing-experience.md) 的语义映射,不照搬 macOS 的物理键位。M4 的验收标准是快捷键表逐项通过。
- 组字期间,快捷键先归系统输入法。界面试做的做法:应用命令在 `canPerformAction` 里检查 `markedTextRange`,组字中一律不响应,Esc 先交给输入法。这一条只管系统输入法的组字;内嵌输入法(§3.6)组字时,切页类命令(⌘N、⌘[、⌘]、⇧⌘L、⌘,)先把组字按原文上屏再执行,字号命令与 Esc 仍不响应(Esc 交给内嵌输入法清掉组字)。
- 键位表如下,已避开系统与 UIKit 的保留键(如 ⌘Tab、地球键)。系统输入法组字期间以上命令一律不响应;内嵌输入法组字期间的例外见上一条。按住 ⌘ 显示快捷键列表只能在 iPad 上测,尚未测。

  | 键位 | 命令 |
  |---|---|
  | ⌘N | 新建一页 |
  | ⌘[ | 上一页 |
  | ⌘] | 下一页 |
  | ⇧⌘L | 纸页列表 |
  | ⌘, | 设置 |
  | ⌘= | 字号 +2 |
  | ⌘- | 字号 −2 |
  | ⌘0 | 字号 22 |
  | Esc | 菜单 |
- 外接键盘输入时,选区变更通知会晚于文字变更到达。凡是“用户挪了光标就退出某状态”的规则(例如退出聚焦打字),都要先记下这次输入后光标应在的位置,紧随输入、且与之相符的选区变更不算挪光标;内嵌输入法落下更新(上屏、清掉组字、换成系统输入法)时引起的选区变更也不算(清掉组字时 UIKit 不经 `shouldChangeTextIn`,光标退回组字之前)。

### 3.3 编辑面的已知坑

状态:[计划:iOS]

以下是界面试做在 iPhone 真机上踩到、并找到解法的问题(见 [§8.1](#81-界面试做))。M1 照这些解法做,除非有更好的办法:

- **聚焦打字时的滚动拉扯**。把当前行滚到视区中线后,`UITextView` 会在插入后自动滚到光标、在内容尺寸变化时校正偏移,两边来回拉扯,画面上下跳。解法:聚焦期间记一个锁定的纵向偏移,覆写 `contentOffset`、`setContentOffset(_:animated:)` 与 `scrollRectToVisible(_:animated:)`,把系统自发的滚动钉回锁定值;手指拖动、减速期间不钉。锁定值按屏幕像素取整,重复居中落在同一位置。
- **TextKit 2 空行的光标偏高**。空段落、文末换行后的那一行,系统给的光标框把行距算在上方,字形区在框的下部;有字的行行距在下方。试做中空行光标比打出第一个字后高出约 17 pt,正好是一个行距。解法:自绘光标时,空行的框顶下移一个行距,再按字号的 ascender 到 descender 居中、按像素取整。
- **TextKit 2 的估算高度**(2026-11-21 真机反馈「切到英文输入时光标有时丢失、上下跳动」,模拟器单元测试复现)。TextKit 2 只排可见区附近的段落,其余段落按估算高度占位。原先编辑面每次内核收下编辑后 `restyle` 对全文重设属性,全文排版随之作废;探针(`LongPageLayoutTests`,约 5 万字、201 段)显示打一键之后光标之前 201 段里有 195 段停在估算值上,内容高度估成 58609pt(实为 109917pt)。`UITextView` 在插入文字时同步算「把光标滚进可见区」,聚焦打字的居中也读光标框,两者都按估算值算:长页里光标落到可见区外(候选行随之隐去),排版补全后又被改正,文字上下跳。英文状态每个字母都是一次上屏、一次 `restyle`,所以最明显。解法:每次文字或选区改变后(`EditorController` 的程序改字之后与选区通知里)从文首排到光标所在段(`SumiTextView.layoutThroughCaret`),下一次插入只作废它自己的段落,滚动目标是实值;不放在 `layoutSubviews` 里,滚动时不重复走 **[我的判断]**(2026-11-21 控制者裁定,取代修正第 1 轮「每次布局排全文」)。
  - `restyle` 只对属性变了的区段 `setAttributes`:先在副本上算出全文应有的属性(基础样式再叠加内核的样式段),与 textStorage 现有的属性逐段比较,只重设不同的那几段。结果与全文重设相同(`EditorControllerTests.test_restyleMatchesAFullReset` 在粘贴、键入、拆段、撤销、换主题之后逐段对照),通常只有键入所在的那一段被作废;换主题、字体、字号时每段都不同,仍是全文重设。不按「改动所在段落」猜范围:粘贴、撤销、引用式链接都可能改远处段落的样式 **[我的判断]**(2026-11-21 第二次终审 I3)。排到光标与候选行摆放前的 `layoutIfNeeded` 照旧保留。
  - 代价(模拟器 iPhone 17 Pro Max、Debug 构建,约 5 万字,`test_keystrokeCostOnALongPage` 各一次运行的中位数):全文重设时,排到光标的每一键光标在文末 40.4ms、在中间 29.6ms(Task 5 三次运行为 39.2–48.6ms、28.7–35.5ms;不排到光标为 27.0ms、21.4ms);只重设变了的区段之后,文末 18.1ms、中间 15.6ms,与不排到光标时(18.1ms、16.1ms)相当,排到光标不再多花时间。探针:不排到光标打一键后,光标之前 201 段里 0 段停在估算值。真机上的每键延迟没量过 [未定]。
  - 粘贴、撤销、重做由内核改字,`UITextView` 不替它们把光标滚进可见区(打字时是它在插入时滚的)。编辑面在这三者之后自己滚一次;聚焦打字时照旧居中 **[我的判断]**(2026-11-21:模拟器上聚焦打字后新建一页再粘贴长文,光标停在可见区外、候选行隐去;`RimeIntegrationTests.test_pastingALongPageScrollsTheCaretIntoView`)。
- **按钮不能叠在 `UITextView` 上**。叠在上面的按钮,点按会先被文本视图的手势接走,按钮收不到。界面外壳的按钮(如菜单)放在编辑区之外单独的一条里。
- **系统光标**。用自绘竖线时覆写 `caretRect(for:)` 改宽高,并关掉系统闪烁,自己控制呼吸;连续输入不重启呼吸的相位。VoiceOver 下的表现未测(见 §7.10)。

### 3.4 打字音

状态:[计划:iOS]

产品规则沿用 [04「打字音」](../04-editing-experience.md):默认开启、可独立关闭;两种音色;只在正文编辑面有焦点时发声,包括中文组字过程;不记录按键内容;命令快捷键不发声;保存失败后被暂停的草稿不发声。iOS 的做法与不同之处:

- **不需要“输入监控”权限**。系统软键盘的按键不经过应用,只能在正文变更时识别按键种类(见 [§2.2](#22-编辑事务的形状)),所以发声只覆盖自己的编辑面,这正好符合“只在正文编辑面有焦点时发声”。
- **播放**:常驻运行的 `AVAudioEngine` 加若干轮换的播放节点,界面试做已在 iPhone 上验证(见 [§8.1](#81-界面试做))。音效样本沿用桌面插件随附的 WAV,不另做一套。
- **线程**:发声不得拖慢输入;音频引擎的启动与样本加载不放在输入路径上。

以下待定:

- 是否受静音键影响 [用户定] 2026-11-21:不受静音键影响。音频会话用 `playback` 类别并与其他应用混音,与试做一致;要静音就在设置里关「打字音」。用户在 iPhone DUO 上反馈「打字没有声音」,原先的 `ambient` 随静音键静音。真机验证 [未定]。
- 修饰键与按键抬起声 [未定]。软键盘拿不到修饰键和抬起事件;接硬件键盘时可以从 `pressesBegan` / `pressesEnded` 拿到,是否据此补上 `thock` 的抬起声,由 M4 定。
- 长按自动重复是否发声,跟随 04 的待定项 [未定]。

### 3.6 实体键盘的内嵌输入法

状态:[计划:iOS]

2026-11-20 用户决定把 rapp 的内嵌 Rime 做法搬进来 **[用户定]**:iOS 上第三方输入法是键盘扩展,接实体键盘后按键不经过它们;所以把 librime 放进应用,在 `pressesBegan` 里把按键交给引擎,组字与候选由编辑面自己画。引擎、按键策略、候选行和 `UITextView` 接线都在独立的共享包 RimeKit 里(本机 `~/git/rime-kit`,GPL-3.0),设计见 [`docs/superpowers/specs/2026-11-20-rime-kit-design.md`](../../superpowers/specs/2026-11-20-rime-kit-design.md)。按键与引擎行为与 rapp 0.15.0 一致,本节只写 Sumi Write 一侧的规则。

- **何时接管**:编辑面有焦点且可编辑、接着实体键盘、状态字不是「系」,这几条同时成立才把按键交给内嵌引擎;否则按键照旧交给系统。打开失败或保存失败而只读时不接管,正在组的字按原文结束(保存失败时内核拒收,正文退回已存的样子)。没接实体键盘(只用软键盘)时,编辑面的行为与没有内嵌输入法时完全相同,候选行不出现。引擎部署期间按键照常交给系统输入法,不卡住打字。
- **状态字** **[用户定]**(2026-11-20 真机试用后的裁定,取代 rapp 的「中 / 英」标签加「内 / 系」按钮):
  - 候选行右端只有一个状态字,紧挨 ›(没有 › 时紧挨最后一个候选):内置输入法中文显示「中」,内置输入法英文显示「英」,系统输入法显示「系」。默认「中」。常显。
  - 与候选同字体同字号,前景色 50% 透明度(半透明)**[用户定]**(2026-11-21 真机试用后的裁定,取代原先的 0.8 倍字号、65% 透明度)。状态字那一块只比字宽左右各多约 4pt,与候选行同高。点击区是这一块,加上它右边正文列以外的页边(那里没有字):在页边里补到 44pt 宽、44pt 高;页边不够宽时点击区就小一些,不向左、也不向下伸到正文上 **[我的判断]**(2026-11-21 控制者裁定,取代此前「向左伸出」的做法:那样小块左侧一块看不见的地方会拦下点正文的点按)。
  - 点它弹出系统原生菜单,三项「中文」「英文」「系统输入法」,当前项打勾。选「中文」或「英文」:用内置输入法,引擎切到对应的中 / 英;选「系统输入法」:组字清掉(不上屏),之后按键全部交给系统输入法。从「系统输入法」选回「中文」或「英文」即切回内置输入法;系统输入法正在组字时(编辑面有它的标记文字)选回不生效,停在「系」,免得内置输入法的组字顶掉系统的那段组字 **[我的判断]**(2026-11-21 第二次终审 I2)。
  - 组字中从菜单切中 / 英,组字先按原文上屏再切,与雾凇左 Shift 的 `commit_code` 一致 **[我的判断]**。
  - 英文状态下字母直接上屏,不组字、不出候选;从菜单切和单按 Shift 切都如此。单按左 Shift 切换中 / 英,状态字随之变;右 Shift 按雾凇的 `default.yaml`(`Shift_R: noop`)不切。
  - 内置与系统输入法的选择记在 `UserDefaults`(键 `rime.builtin`),重开应用保留;中 / 英不另存,引擎每次启动是中文(雾凇的 `save_options` 不含 `ascii_mode`)**[我的判断]**。外观面板里不加「内 / 系」开关 **[我的判断]**(设计 §0 第 5 条);面板里只有下一条的快捷键。
  - 这是 RimeKit 的一个选项,默认保持 rapp 的样子,Sumi Write 打开它。
- **切换中 / 英的快捷键** **[用户定]**(2026-11-21「切换输入法,能否有快捷键 响应 ctrl+space 之类的,可以在设置中设置」;下面的做法是控制者的裁定 **[我的判断]**):

  - 单按左 Shift 照旧切换中 / 英,不受这项设置影响。
  - 识别快捷键在 RimeKit 的适配器里(`RimeTextViewAdapter.switchShortcut`,默认「关」,保持 rapp 的样子),应用只把设置值传进去。

- **候选行盖住下一行** **[用户定]**:候选行带主题底色、不透明,叠在光标所在行的下一行上,从正文左缘开始、宽度为正文列宽,打字时不随光标横移。接着实体键盘、编辑面有焦点时一直显示(选「系」时也显示,好让用户切回内置输入法)。没有组字、没有候选时,候选行收窄成只包住右端状态字的不透明小块(左右各留约 4pt,与候选行同高),不盖住下一行其余的字;点在小块及其右侧页边里的点击区以外(包括小块紧左边和正下方)都落到正文上;部署中或出错时照旧整行显示消息。字体与正文同字体同字号;文字为主题前景色,序号为前景色 65% 透明度,高亮候选用主题强调色(主题没有强调色时用前景色)。
- 候选行的其余细节 **[我的判断]**(设计 §5.3):
  - 候选行是文本视图的兄弟视图,放在渐隐遮罩之外的最上层,不被聚焦打字的渐隐淡掉;按钮不叠进 `UITextView`(见 [§3.3](#33-编辑面的已知坑)),候选、‹ ›、状态字都能点中。
  - 聚焦打字时当前行居中,候选行的位置因此固定;不在聚焦打字时,候选行跟着光标所在行上下移动,只在换行时移动,同一行里打字不动。
  - 光标所在行已是视区最后一行时,先把正文上滚一行,让候选行留在视区里。

  - 字号变了,候选行的高度与位置随即跟着变。候选行出现或消失时正文底部的留白跟着变,滚动位置夹回可滚范围,不留空白。
- **组字**:组字以标记文字(`setMarkedText`)插在光标处,带下划线,后文照常回流。组字中的文字不进内核(§2.2 的判定照样成立),上屏时整段作为一次编辑交给内核,光标在上屏文字之后。
- **组字期间正文不接受改动**:内嵌输入法组字时,点击挪光标、粘贴、撤销与重做、拖入文字一律不响应(rapp 编辑器同一条规则:否则在旧位置上屏后又在新位置重新组字)。
- **上屏**:失去焦点、切页、打开概览或设置、进后台时,内嵌输入法的组字按原文上屏,进内核,不丢。切页、打开概览或设置之前、以及失去焦点时的这次上屏不算打字:不发打字音,不进聚焦打字。这是 [04「组字期间暂缓远端更新」](../04-editing-experience.md)「切换操作不能擅自提交组字」的 iOS 例外:那一条防的是替系统输入法提交它的组字;内嵌输入法的组字归应用自己,先上屏再切换。
- **切页与组字**:系统输入法组字时照旧拦住切页,提示「请先完成输入」;内嵌输入法组字时先上屏再切页。
- **设置页脚注**:「输入法」一组下方有一行脚注,说明接实体键盘时用内置输入法切换中 / 英,单按左 Shift 也能切换;选「Shift + 空格」时再加一句「按着 Shift 打完大写字母紧接着按空格,也会切换」**[我的判断]**。
- **词库**:只用内置的雾凇(rime-ice)。「我的目录」(文件共享、用户自己的 `default.yaml`)这一轮不做 **[我的判断]**(设计 §0 第 4 条)。
- **打字音**:内嵌输入法接管的按键,每按下一次发一声,种类按键码分(空格、回车、退格、其余为普通键),修饰键(⇧、⌃、⌥、⌘、大写锁定)被接管也不发声,它引起的组字与上屏不再另发声;其余规则同 [§3.4](#34-打字音)。点候选、按住键时引擎自己的连发等不经按键入口的上屏,按文字变化发声;既没按着键、也不是点候选的上屏(如应用失去活跃时引擎自己上屏)不发声、不算打字 **[我的判断]**。
- **许可证**:RimeKit 与雾凇都是 GPL-3.0,打进应用的二进制包含雾凇的数据。第一阶段只自用、不公开发行,眼下没问题;公开发行前要一起处理(设计 §3)。
- 真机未验证:本节在模拟器上有自动测试,真机验收清单见 [`apps/ios/README.md`](../../../apps/ios/README.md)「内嵌输入法」一组;真机验收通过前状态行不变。

## 7. 工程待答问题

本节收集 iOS 实现前必须回答、但设计与本附录都还没有答案的工程问题。每一项都 [未定],由对应里程碑的计划给出答案;答案定下后写回上文对应小节。

### 7.1 UniFFI 接口形状

状态:[未定]

- `session/` 经 UniFFI 暴露的接口用同步调用还是异步调用;回调(远端更新、持久事件)在哪个线程上回到 Swift;错误怎样映射成 Swift 的错误类型。由 M0 定。
- M1 的答案见下,交付后改状态。只覆盖 `core`,`session/` 尚不存在:
  - 用 UniFFI 过程宏(`setup_scaffolding!`、`uniffi::Object`/`Record`/`Error`),不写 UDL。文档与存储各包成一个对象,内部加互斥锁;Swift 侧拿到的是引用计数的类。
  - 全部同步调用。内核在真机上每次逐字替换 p95 约 2.1 ms,同步调用在输入线程上可以接受;落盘 p95 约 4.3 ms、偶有约 50 ms 的尖峰,按 §2.1 放到后台线程。
  - 错误映射成带关联值的 Swift 枚举,修订过期、偏移非法(切开字素)可以在 Swift 里分别捕获。
  - 暴露的面只覆盖 M0、M1 要用的内核能力:建文档或从库打开、带修订号的 UTF-16 替换、正文与修订号、按行快照(行 ID、首写与末写时间、时间来源)、撤销与重做(含 `canUndo` / `canRedo` 查询)、合并更新、库的写入与检查点。UniFFI 版本钉 `=0.32.2`。
  - 回调与线程归属留给 `session/`。

### 7.2 异步运行时、后台与数据保护

状态:[未定]

- 内核与会话在 iOS 上用哪种异步运行时、由谁持有其生命周期。
- 应用被挂起或锁屏时 WebSocket 连接怎样处理,回到前台怎样重连。
- 纸页 SQLite 文件用哪一档 Data Protection 等级;锁屏后仍需写入时,与输入日志的落盘要求是否冲突。由 M2、M3 定。

### 7.3 iPad 多场景与单一编辑 owner

状态:[未定]

- iPad 上多个窗口场景打开同一页时,怎样与“同一页只有一个编辑 owner”的规则相容(拒绝、只读,还是转交 owner)。桌面现行规则见 [notemd-desktop §3.1](notemd-desktop.md)。由 M4 定。

### 7.4 字体注册与下载策略

状态:[未定]

- 下载后的字体用 CTFontManager 注册在哪个作用域(进程内还是更大范围)。
- 七个字体文件合计约 93.9 MB(见 [05-fonts](../05-fonts.md)),蜂窝网络下是否允许下载、本机存储吃紧时怎样处理,尚无策略。

### 7.5 落盘保证

状态:[未定]

- 桌面 macOS 依靠 SQLite 的 `synchronous=FULL` 与 `fullfsync`(见 [notemd-desktop §8.1](notemd-desktop.md))。iOS/APFS 上是否同样设置、`F_FULLFSYNC` 的实际效果,都没有设计,也没有测试。由 M2 定。

### 7.6 互操作夹具的路径

状态:[未定]

- M0 要在 Swift 侧加载现有的互操作夹具。第 1 期把 `write-core` 改名为 `core/` 后,夹具路径是 `core/tests/fixtures/yrs-v1.json`;iOS 测试怎样引用它(复制、链接还是构建时生成),由 M0 定。
- M1 的答案见下,交付后改状态:夹具在构建时由 `golden` 生成并复制。构建脚本把 Rust 夹具、Yjs(JS)夹具复制进应用包;再用同一份内核编译一个桌面命令行工具,生成两样东西:一是“桌面写的库”(含检查点和其后的增量),二是比对基准(按与 Swift 完全相同的步骤跑一遍夹具后的完整快照)。Swift 侧逐字段比对快照,包括行 ID、首写与末写时间、时间来源。基准由内核生成,Swift 不复述任何期望值。

### 7.7 XCFramework 目标与工具链

状态:[未定]

- XCFramework 至少包含真机 arm64 与模拟器 arm64 两个目标;是否还要模拟器 x86_64,未定。
- Rust 工具链要与桌面一致,钉在 1.99(见 [02-migration-plan](../../handoff/02-migration-plan.md) 第 1 期);iOS 目标怎样随同钉住,由 M0 定。
- M0 试做的发现:
  - 真机 arm64 加模拟器 arm64 两个静态库,用 `xcodebuild -create-xcframework` 打包,在 Apple 芯片的 Mac 上够用;没有试 x86_64。
  - `rusqlite` 的内置 SQLite 能直接交叉编译到两个 iOS 目标,不需要改 `write-core`。
  - 必须设置 `IPHONEOS_DEPLOYMENT_TARGET`,与应用的最低系统一致;不设时,内置 SQLite 的目标文件按构建机 SDK 的版本编译,链接时报“目标文件比被链接的版本新”。
  - 试做用的是本机已有的 stable 1.99.1,不是钉住的 1.99.0。
- M1 的答案见下,交付后改状态:构建脚本用 `cargo +1.99.0`,目标只有 `aarch64-apple-ios` 与 `aarch64-apple-ios-sim`,不含模拟器 x86_64;并设置 `IPHONEOS_DEPLOYMENT_TARGET=17.0`,与应用一致。

### 7.8 撤销归属

状态:[未定]

- 撤销交给 CRDT 撤销 owner 时,UITextView 自带的撤销栈怎样关闭或接管(见 §2.2)。两次试做都没有碰这件事。
- M1 的答案见下,交付后改状态:关掉 `UITextView` 自带的撤销栈,改为转发给内核 `undo` / `redo` 的 `UndoManager` 子类,三指手势、摇一摇和硬件键盘的 ⌘Z / ⇧⌘Z 都走内核。粒度一次事务一步(内核 `capture_timeout_millis: 0`,与桌面一致)。撤销后重建 `SourceMap`,光标放在变化区末尾。

### 7.9 内存预算

状态:[未定]

- 同步协议允许客户端一次完整回放最多 65 MB(见 [03-sync](../03-sync.md));这在 iPhone 上的内存预算是否可接受、要不要分段回放,未评估。由 M3 定。

### 7.10 VoiceOver 与自绘光标

状态:[未定]

- 自绘光标时,VoiceOver 怎样获得插入点与选区位置;系统光标隐藏后,无障碍行为不能退化。
- M1 的答案见下,交付后改状态:光标不再是叠在文本视图上的自绘层,而是经系统 `cursorView` 接口换上的 `SumiCursorView`(取代系统细光标的主题色竖线),插入点与选区仍由 `UITextView` 的系统文本输入机制承载,没有额外的自绘覆盖层需要对无障碍隐藏;VoiceOver 仍能读正文,并报告插入点与选区。

## 8. 试做记录

本节记录两次一次性试做的结论。试做代码在本机的独立目录里,不进本仓库,也不算交付;这里的每条结论都只作为 M0、M1 计划的输入。

### 8.1 界面试做

状态:[计划:iOS]

- **时间与设备**:2026-11-19,iPhone 真机(iOS 27.2),部署目标 iOS 18.0。iOS 17 未验证。代码在本机 `~/git/sumiwrite-ios-spike`,未进版本管理。
- **范围**:纯 Swift 的一页纸写作界面,不接内核,纸页存成本机文件。做了自绘呼吸光标、六种主题与字号、聚焦打字(当前行居中、上下文渐隐)、纸页切换、硬件键盘命令、打字音效。
- **结果**:真机上 10 项手工测试全部通过。踩到并解决的问题已写进 [§2.2](#22-编辑事务的形状)、[§3.2](#32-键盘避让与硬件键盘)、[§3.3](#33-编辑面的已知坑)、[§3.4](#34-打字音)。
- **打字音效**:用常驻运行的 `AVAudioEngine` 加 8 个轮换的播放节点,普通键、空格、回车、退格各一个样本;常驻引擎让扬声器保持唤醒,几十毫秒的短点击不会被启动延迟吞掉。试做把音频会话设成 `playback` 并与其他应用混音,所以不受静音键影响;正式版是否该受静音键影响,未定。
- **没测的**:iPad(按住 ⌘ 的快捷键列表、分屏、指针)、VoiceOver、撤销。

### 8.2 M0 内核试做

状态:[计划:iOS]

- **时间与设备**:2026-11-20,模拟器(iPad Pro 11 英寸,iOS 26.5)与 iPhone 真机(iOS 27.2),部署目标 iOS 18.0。代码在本机 `~/git/sumiwrite-m0-spike`,未进版本管理。
- **做法**:把 note.md 现有的 `write-core` 原样经 UniFFI 暴露给 Swift,桥接层只做类型转换和加锁,不含任何文档、行时间或合并逻辑。应用启动即跑自检;另有一个“用内核写字”的编辑面,每次上屏都经内核成为一次事务并写进 SQLite。
- **自检项**(模拟器、iPhone 真机均 9/9 通过):
  1. 内核加载;
  2. Rust 夹具按序合并、倒序合并、完整状态三种方式,快照与 Rust 测试的期望值逐字段一致(行 ID、首写与末写时间、时间来源);
  3. Yjs(JS)夹具合并后正文一致;
  4. 读桌面写的库:检查点加其后的增量,恢复出的快照与桌面一致;
  5. iOS 写库、关闭、重开:中英文、emoji、组合字逐字写入并中途做检查点,重开后快照一致;
  6. 错误映射:修订过期、切开 emoji 两种错误能在 Swift 里分别捕获;
  7. 性能:约 6200 字的纸页上逐字输入 1000 次。真机:内核替换 p50 1.6 ms、p95 2.1 ms、最大 2.5 ms;每次落盘 p50 3.3 ms、p95 4.3 ms,最大 49.7 ms。模拟器:内核替换 p95 1.1 ms,落盘 p95 4.5 ms。落盘偶有数十毫秒的尖峰,印证了 §2.1“持久化在后台线程做”。
- **反向核对**:把模拟器和真机写的库分别拷回 Mac,用同一份内核读出,正文、行数与行时间与 iOS 一致。
- **强杀恢复**(真机手测,用户执行):在“用内核写字”编辑面用拼音输入法写中英文,从多任务界面划掉应用再打开,正文完整,每行都有首写与末写时间。
- **未覆盖**:撤销、远端同步、`session/`(尚不存在)。
- **结论**:路线的前半段成立:`write-core` 不改一行就能进 iOS,模拟器与真机上夹具结果都与 Rust 测试一致,性能余量充足。M0 的正式验收仍以 M0 计划为准。
